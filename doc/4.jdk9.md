# JDK 9

IKVM currently implements Java SE 8. This document describes how JDK 9 support can be added *alongside* the existing
JDK 8 support — built from the same repository and the same branch — and records the architectural decisions that
make that possible.

It is a design document, not a work plan. It exists because the JDK 9 effort is large enough to span many releases,
and work spread over that long a period needs a written account of why things are shaped the way they are. Tracking
issues [#120](https://github.com/ikvmnet/ikvm/issues/120) and [#665](https://github.com/ikvmnet/ikvm/issues/665)
carry the discussion; this carries the conclusions.

## The problem

Adding JDK 9 is not one change. It touches:

- the `ext/openjdk` submodule, which is pinned to `ikvmnet/jdk8u`;
- `src/IKVM.Java/IKVM.Java.runtime.jdk.{props,targets}`, ~2,300 lines of MSBuild that hand-port the OpenJDK 8
  makefiles, including 31 code-generation targets;
- `src/IKVM.Java/map.xml`, 2,899 lines remapping 69 Java classes onto CLR types;
- `src/IKVM.Java/local/`, 119 hand-written `.java` files replacing OpenJDK classes;
- 36 `.clangproj` native library projects, whose source globs assume the JDK 8 layout;
- `IKVM.Runtime`, 425 files and ~95,000 lines.

None of that can land at once. The organising question is therefore not "how do we implement JDK 9" but **"how do we
arrange the repository so that JDK 9 work can arrive in small pieces, over years, without destabilising the shipping
8.x line."**

The single most important structural answer is that **the existing coupling between `IKVM.Runtime` and `IKVM.Java`
should be reduced before the JDK 9 tree is created, not worked around afterwards.** That coupling is what forces the
four-stage bootstrap, and — left in place — it would force the JDK 9 port to reintroduce JDK 8 internals into a JDK 9
source tree permanently, in service of scaffolding. ADR-1 covers this and most other decisions here follow from it.

## Principles

These constrain every decision below, and some of them cut against the shortest path:

1. **Every release must be good on its own terms.** Work is sequenced so that each step ships as a defensible 8.x
   improvement, not as a partially-migrated intermediate state. A change that only makes sense in the light of some
   later change does not go in.
2. **Calendar time is not a constraint; quality is.** Arguments of the form "that is a lot of work" carry no weight
   here. Arguments of the form "that degrades emitted code", "that regresses the dynamic class-loading path", or
   "that makes the 8.x line non-conformant" are decisive. Where this document declines to do something, the reason
   must be of the second kind — and if it is not, the decision is wrong.
3. **Prefer removing a constraint to managing one.** Where scaffolding exists to work around a design problem,
   fixing the design problem is preferred over building better scaffolding, even when the scaffolding is cheaper.
4. **Deviations from the JDK are stated, not absorbed.** Where IKVM cannot or will not match Java semantics, that
   belongs in user-facing documentation rather than in a comment.

## What the code looks like today

### The bootstrap cycle is a symptom of one dependency

IKVM breaks the `IKVM.Java` ↔ `IKVM.Runtime` cycle with a four-stage build: `IKVM.Java-ref` (61 hand-written C#
stubs, `AssemblyName=IKVM.Java`) → `IKVM.Runtime-ref` (all of `../IKVM.Runtime/**/*.cs` recompiled with
`FIRST_PASS`) → `IKVM.Java` (ikvmc, `-bootstrap`) → `IKVM.Runtime`. `IKVM.Tools.Importer` and `IKVM.Tools.Exporter`
are two further compilations of the same sources under `IMPORTER` and `EXPORTER`. Six compilations, across three
target frameworks.

All of that scaffolding exists to work around **one arrow**: `IKVM.Runtime` has a compile-time dependency on
`IKVM.Java` (`IKVM.Runtime.csproj` `ProjectReference` to `IKVM.Java.ikvmproj`). The reverse arrow — compiled Java
code calling `ByteCodeHelper` and the externs — is essential and cannot be removed. The forward arrow can be.

That arrow is much smaller than the scaffolding suggests:

| | files |
| --- | --- |
| guarded by `FIRST_PASS` | 191 |
| **actually referencing `java.*` / `sun.*`** | **67** |
| guarded but not coupled | 128 |

The entire 58-file `Accessors` layer is guarded by `FIRST_PASS` and references **zero** Java types — it is already
decoupled by construction. Roughly two thirds of the `FIRST_PASS` tax is accidental rather than essential.

Of the 67 genuinely coupled files, 48 are externs. Outside the externs there are 19 files, dominated by one:

```
ByteCodeHelper.cs                        123 refs
MethodHandleUtil.jniexport.cs             14
Util/Java/Net/SocketExceptionExtensions   11
NativeInvokerBytecodeGenerator.cs          8
… everything else ≤ 4
```

Outside the externs there are 58 distinct referenced types, of which 90 references are exception and error types —
constructed and thrown, and `ExceptionHelper` already exists as a seam for that. The genuinely hard residue is
`java.lang.invoke`: **12 distinct types** (`MethodType`, `MethodHandle`, `MethodHandles.*`, `LambdaForm`,
`MemberName`, `MethodHandleNatives` and relatives) sitting on the JSR292 hot path, several at IL-*emission* sites
where indirection changes generated code rather than merely slowing it.

Two mechanical facts make the reduction less invasive than it looks — neither requires redesigning a mechanism:

- **Extern signatures need not be tightly typed.** Binding is by naming convention plus
  `IsCompatibleArgList` (`RuntimeByteCodeJavaType.FinishContext.cs:2084`), which tests `IsAssignableTo` — not exact
  identity. An extern may therefore declare `object` where it currently declares `global::java.lang.Class`.
- **`java.lang.Object`, `String`, `Throwable`, `Class` and friends are remapped, not referenced.** They are among
  `map.xml`'s 69 remapped classes, so they are not ordinary compile-time dependencies.

### There is a second, unrelated coupling

77 files use `using Type = IKVM.Reflection.Type`. `MethodAnalyzer.cs`, `CodeEmitter.cs` and `compiler.cs` contain
*zero* `FIRST_PASS` but carry `IMPORTER` throughout: they are recompiled for ikvmc not because of Java coupling but
because the same type-model code must run against two different reflection stacks.

`src/IKVM.CoreLib/Symbols/` (44 files — `ITypeSymbol`, `IAssemblySymbol`, `ISymbolResolver`, with `IkvmReflection`
and `Reflection` backends) exists to unify them, but is wired into only 4 files in `IKVM.Runtime` and 2 in the
importer. It is a started, stalled migration. See [Non-goals](#non-goals).

### A JPMS implementation already exists, and nothing uses it

`src/IKVM.CoreLib/Modules/` is 31 files and 4,861 lines — a C# port of `java.lang.module` and `jdk.internal.module`.
It contains `ModuleDescriptor` and its builder, `ModuleFinder`/`ModulePath` (handling modular jars, exploded modules,
and automatic modules including `Automatic-Module-Name`), `JarModuleReader`, `ExplodedModuleReader`,
`InMemoryModuleFinder`, a 663-line `ModuleResolver`, `ModuleConfiguration`, and a full JEP 223 `RuntimeVersion`
parser. Its `README.txt` states the intent plainly:

> The importer and exporter will use this to build a module graph from existing Java code for transpilation.

It is tested end to end: `src/IKVM.CoreLib.Tests/Modules/` builds fixtures with JDK 21 `javac --release 9 -p …` into
`src/IKVM.CoreLib.Tests/res/Modules/{m1,m2,m3,m4,automatic}`.

It is referenced only by `IKVM.Util/Jar/*`, `IKVM.CoreLib/Jar/JarFile.cs`, and
`IKVM.MSBuild.Tasks/IkvmReferenceItemPrepare.cs`. Neither `IKVM.Tools.Importer`, nor `IKVM.Tools.Exporter`, nor
`IKVM.Runtime` touches it. It has readers but no writer.

The compiler-side half of #665 is therefore largely written and merely unwired — and wiring it requires no JDK 9
source tree at all.

### Class loading is assembly-driven, lazy, and forgiving

This is the part of the runtime that JPMS collides with, so it is worth stating precisely. See
[Class Loading](3.classloading.md) for the user-facing view.

`ikvm.runtime.AssemblyClassLoader` calls `super(null)` — it has **no parent**. Delegation instead follows the .NET
assembly reference graph: `RuntimeAssemblyClassLoader.DoInitializeExports` populates `references` from either the
`ikvm.exports` manifest resource or `Assembly.GetReferencedAssemblies()`, and `FindReferenced` walks that array,
materialising a delegate loader per reference on demand.

Three properties matter here:

- **One loader per assembly.** `RuntimeAssemblyClassLoaderFactory.FromAssembly` caches a
  `RuntimeAssemblyClassLoader` per `Assembly`. The single exception is `-sharedclassloader` groups, where assemblies
  carrying a `__<MainAssembly>` forwarder all resolve to the group's main loader.
- **The loader set grows at runtime.** Loaders are created on demand as assemblies appear, and `LoadDynamic` can
  define classes from resources found anywhere in the delegation graph.
- **Missing references degrade silently.** `LoadAssemblyOrClearName` catches every exception, caches the failure by
  nulling the name, and returns; `TryGetLoaderByIndex` skips it. An absent optional dependency is a
  `ClassNotFoundException` at the point of use, never a startup failure.

Packages are also defined lazily — `AssemblyClassLoader.lazyDefinePackages` runs on first `getPackage`/`getPackages`,
reading `PackageListAttribute` off each .NET module of the assembly (`RuntimeAssemblyClassLoader.GetPackageInfo`,
returning `(container, packages[])` pairs).

### What JPMS actually requires

The relevant constraints were verified empirically against JDK 21 rather than taken from specification prose, because
one of them is commonly overstated — including in #665, which asserts that "only one Module in a Layer and it's
hierarchy can possess a single Package."

Given two modules that both contain package `p`:

| Operation | Result |
| --- | --- |
| `Configuration.resolve` over both | succeeds — split packages resolve fine |
| `defineModulesWithOneLoader` | `LayerInstantiationException: Package p in more than one module` |
| `defineModulesWithManyLoaders` | succeeds |
| named module reads unnamed module by default | no |
| `jdk.internal.module.Modules.addReads(named, unnamed)` | succeeds — the JDK's own `--add-reads` path |
| define a module containing `p` *after* a class in `p` loaded into that loader | `LayerInstantiationException: Package p for module m1 is already in the unnamed module defined to the class loader` |

Two conclusions follow, pointing in opposite directions:

**The package-uniqueness rule is per class loader, not per layer.** IKVM's one-loader-per-assembly design therefore
already satisfies it: two assemblies may contain the same Java package, or the same `cli.*` namespace, without
conflict. The `-sharedclassloader` case — several assemblies, one loader — is the one place uniqueness must hold
across assemblies, and ikvmc already enforces it by giving the whole group a single shared package list
(`ImportClassLoader.cs:2893-2897`, emitted once at `:612`). The objection in #665 that namespace overlap between
assemblies makes assembly-to-module mapping impossible does not hold.

**Modules cannot be defined opportunistically.** Once a class loader has defined a package into its unnamed module,
no named module containing that package can ever be defined to that loader. Since `AssemblyClassLoader` loads classes
and defines packages lazily, a module must be defined at the moment its loader is constructed — before anything in it
loads — or not at all.

### Externs bind through a single hard-coded namespace

Native methods are implemented in C# under `src/IKVM.Runtime/Java/Externs/` and bound by ikvmc at static-compile
time. The binding is one line, `src/IKVM.Runtime/RuntimeByteCodeJavaType.FinishContext.cs:395`:

```csharp
var nativeCodeType = context.Resolver.ResolveRuntimeType("IKVM.Java.Externs." + classFile.Name.Replace("$", "+")).AsReflection();
```

A single root, resolved by exact name. It is tempting to assume a second extern tree could simply be added alongside
the first — it cannot. The two would collide on precisely the classes needing different bodies (`java.lang.System`,
`Class`, `Thread`, `ClassLoader`, `sun.misc.Unsafe`, `java.lang.invoke.*`). The tree is also internally cross-coupled
by direct C# calls between extern classes, so it is not a clean unit to copy either.

Making that root an ordered probe list is the smallest change that unblocks a second tree, and it does not exist yet.

### Version ceilings are narrower than they look

`src/IKVM.Runtime/ClassFile.SupportedVersions.cs` declares `Minimum = 45` and `Maximum = 52`, but the type has no
references anywhere outside its own declaration — it is dead code. The only live ceilings are two literals:

```
src/IKVM.Runtime/ClassFile.cs:357   if (reader.Version < new ClassFormatVersion(45, 3) || reader.Version > 52)
src/IKVM.Runtime/ClassFile.cs:386   if (clazz.Version  < new ClassFormatVersion(45, 3) || clazz.Version  > 52)
```

Every other version test — `< 49`, `< 51`, `>= 52` across `ClassFile.*`, `MethodAnalyzer.cs`, `compiler.cs`,
`RuntimeByteCodeJavaType.JavaTypeImpl.cs` — is a *backward*-compatibility gate. Those stay correct verbatim as the
ceiling rises; they do not need auditing.

`ClassFile.cs:357` is the IMPORTER-only `GetClassName`, which ikvmc calls on every input file. A v53
`module-info.class` therefore fails before ikvmc ever inspects it. Module class files must bypass
`IKVM.Runtime.ClassFile` entirely and go to `ModuleDescriptor.Read`, which consumes the raw `IKVM.ByteCode` class
file.

### The Java version is stamped into the runtime at build time

`src/IKVM.Runtime/JVM.Constants.cs.tt` is token-substituted during the build from the global `OpenJdk*` properties in
`Directory.Build.props`, producing `java_version`, `java_specification_version`, `java_runtime_version` and friends.
`JVM.Properties.InitSystemProperties` consumes them, and also sets `java.ext.dirs`, `java.endorsed.dirs`, and
`sun.boot.class.path` — all JDK 8 concepts with no meaning under JPMS.

A runtime binary shared between flavors cannot be stamped `1.8`.

### Other constraints worth stating

- `src/IKVM.NET.Sdk/targets/IKVM.Java.props` sets `<LangVersion>1.8</LangVersion>` and `<JavaVersion>1.8</JavaVersion>`
  unconditionally, so no project — in this repo or in a consumer's — can override them.
- `targets/openjdk.buildtools.targets` compiles the OpenJDK build tools with `-source 1.8 -target 1.8` and requires
  `$(JdkPath)/lib/tools.jar`. JDK 9 has no `tools.jar`, moved the build tools to `make/jdk/src/classes`, and does not
  export the `jdk.compiler` internals they use.
- `targets/openjdk.lib.props` maps RIDs to `windows`/`solaris` source directories. JDK 9 restructured the native
  layout entirely (`src/java.base/{share,unix,windows,macosx}/native/libjava/…`), invalidating all 36 clangproj globs.
- `FindJdk Family="8"` appears in `src/IKVM.Java/IKVM.Java.runtime.targets`,
  `src/IKVM.Image/IKVM.Image.project.targets`, and `src/javac-ref/javac-ref.ikvmproj`. `IKVM.CoreLib.Tests` already
  uses `Family="21"`, and CI already installs `openjdk-21-jdk` without using it.
- `ikvmc` does not use `IKVM.CoreLib.Jar.JarFile`. `ImportContext.ProcessZipFile` calls `ZipFile.OpenRead` directly,
  and `ProcessManifest` reads only `Main-Class:`.
- `IKVM.CoreLib/Jar/JarFile.cs:23-27` pins `BASE_VERSION` and `RUNTIME_VERSION` to `8` and sets
  `MULTI_RELEASE_ENABLED = false`. The versioned-entry plumbing behind those pins is written and short-circuited.
- CI builds everything in one `build-ikvm` job with a 720-minute timeout, cross-compiling 11 RIDs, already requiring
  manufactured swap space and aggressive disk cleanup. It cannot absorb a second full build.

## Decisions

### ADR-1 — Reduce the `IKVM.Runtime` → `IKVM.Java` dependency before creating the JDK 9 tree

**Context.** The forward arrow from `IKVM.Runtime` to `IKVM.Java` is the sole cause of the four-stage bootstrap, and
it is carried by 67 files rather than the 191 that `FIRST_PASS` guards. Left in place, it does not merely make the
JDK 9 port more expensive — it makes the port fight itself. `IKVM.Runtime` references private and package-private
members such as `DirectMethodHandle._preparedLambdaForm`, `LambdaForm.LAST_RESULT` and `MemberName.CALLER_SENSITIVE`;
if a JDK 9 base library must satisfy those, the JDK 9 tree has to *reintroduce JDK 8 internals permanently*, in
service of scaffolding.

**Decision.** Reduce the dependency to a small, stable residual core first. Four steps, in order:

1. Remove `FIRST_PASS` from the 128 guarded-but-uncoupled files. Pure deletion; the proof is that all six
   configurations still compile.
2. Loosen extern signatures to `object` where they currently name Java types, relying on `IsAssignableTo` binding.
   This is the 48-file bulk and is mechanical.
3. Route `ByteCodeHelper`'s exception construction through the existing `ExceptionHelper` seam — 90 of the
   non-extern references are exception and error types.
4. Hold at the ~12 `java.lang.invoke` types as a residual core, unless and until a way is found to remove them that
   does not degrade generated code or the MethodHandle path.

**Alternatives rejected.** *Building the JDK 9 tree first and decoupling later* — rejected on sequencing: a tree
built against the current constraints is shaped around satisfying JDK 8-isms, and decoupling afterwards leaves
vestigial shims that were never necessary.

*Driving the dependency to zero by accessor-ising `java.lang.invoke`* — rejected on quality, not on effort. Several
of those references are at IL-*emission* sites (`MethodHandleUtil.root.cs`, `intrinsics.cs`, `compiler.cs`), where
replacing a typed reference with a late-bound one changes the code IKVM generates rather than merely slowing the
compiler down. The remainder sit on the JSR292 invocation path, where delegate indirection is paid by every user of
every release. Both are per-release quality costs, which principle 2 treats as decisive.

**Consequences.** Step 4 is a holding position, not a conclusion. A residual core of a dozen types that are unchanged
from Java 8 through Java 25 is trivially satisfiable, whereas today's 67-file surface is a standing hazard — so the
holding position is defensible indefinitely. But it is worth noting that the residual coupling is unusual in kind:
IKVM does not merely *use* these types, it *patches* them. `DirectMethodHandle._preparedLambdaForm` is a field IKVM
adds; `LightWeightMethodHandle` is a class IKVM invents. A third option therefore exists that is neither "keep the
coupling" nor "hide it behind accessors" — relocating IKVM's JSR292 support surface into `IKVM.Runtime` proper, so
that the remaining `java.lang.invoke` references are to types IKVM owns. Whether that is achievable without breaking
the requirement that these *be* `java.lang.invoke` types to Java code is unresolved; see
[Open questions](#open-questions).

Because the residual surface still exists, a compile-time reference to `IKVM.Java` remains, and with it the identity
constraint in ADR-2 — but it becomes narrow and stable rather than sprawling.

The natural stopping condition is otherwise absent, so **the contract verifier is built first, as a measurement
instrument**: point it at `IKVM.Runtime.dll`, have it walk the TypeRef/MemberRef tables for references into assembly
`IKVM.Java`, and report the surface. Step 1 must then provably remove 128 guards without changing that number, and
"stop" becomes a threshold rather than a judgement call. IKVM.Reflection is already a dependency, so this is a small
tool; once the JDK 9 tree exists, the same tool resolves the residual surface against it.

This also shrinks the compatibility surface the JDK 9 tree must carry. Some IKVM-private types will still be needed
where `map.xml` remaps demand them — `sun.reflect.Reflection` and `sun.invoke.util.VerifyAccess` are among the 69
remapped classes, and a remap cannot be replaced by a forwarder — but this becomes a bounded, shrinking list rather
than an open-ended permanent obligation. Where such types are added to the JDK 9 `local/` overlay they should be
commented as deliberate, so a later contributor does not "fix" them by deletion.

### ADR-2 — One `IKVM.Runtime.dll` serves both JDK flavors

**Context.** Forking the runtime per JDK version would double the maintenance surface of the hardest code in the
project, and the bootstrap chain means the fork would really be twelve compilations rather than six.

**Decision.** Ship one `IKVM.Runtime.dll`, compiled against the JDK 8 `IKVM.Java` reference assembly. The JDK 9
`IKVM.Java` must be a superset of whatever referenced surface survives ADR-1.

This is feasible because `IKVM.Java.ikvmproj`'s `ConvertRefAssembly` target runs refasmer with
`--refasm --overwrite --noattr --all`: the assembly `IKVM.Runtime` compiles against carries type and member *shapes*
only. The entire metadata contract — `RemappedClassAttribute`, `PackageListAttribute`, class maps — is discovered at
runtime from whichever assembly is actually loaded, via `AttributeHelper`.

**Consequence — assembly identity.** All assemblies are strong-named from the checked-in `ikvm.snk`, and
`AssemblyVersion` derives from `DefaultMajorVersion`, which is `8`. Because IKVM's major version tracks the Java
version it implements, the natural-looking move is to build the JDK 9 flavor as `9.0.0.0`. **It must not be.**
`IKVM.Runtime.dll` carries a baked `AssemblyRef` to `IKVM.Java, Version=8.0.0.0`; .NET Core has no publisher policy,
so the reference would simply fail to resolve, and .NET Framework would need binding redirects. The JDK 9 flavor
keeps `AssemblyVersion = 8.0.0.0`; the "9-ness" lives in the `OpenJdk*` properties and in a base-assembly attribute.
`DefaultMajorVersion` is not touched.

The two flavors therefore share an assembly identity and are **mutually exclusive** — on disk, in a NuGet package,
and in a process. They need separate output roots and separate test processes. This constraint is a direct
consequence of the surviving reference; if ADR-1 ever reduced it to nothing, the constraint would lift.

**Alternatives rejected.** Forking the runtime per flavor — rejected on maintenance cost. Making the runtime fully
JDK-agnostic — see ADR-1, rejected for the `java.lang.invoke` cluster.

### ADR-3 — No new conditional-compilation symbol

**Context.** `IKVM.Runtime` is compiled six times under different symbols across three target frameworks. ADR-1
reduces the `FIRST_PASS` surface substantially but does not eliminate the multiplicity.

**Decision.** JDK-flavor differences are expressed as **data**, not as C# conditionals: MSBuild source globs,
`map.xml`, and the `local/` overlay. Where the runtime genuinely must behave differently, it branches on a single
integer feature version read once from an attribute on the loaded base assembly.

**Alternatives rejected.** A seventh compilation symbol — rejected; it compounds the bootstrap problem and every
future change would need testing under both. Runtime capability probing ("does `java.lang.Module` exist?") — rejected
as fragile and *late*: by the time `JVM.Init()` runs, boot decisions have already been made. Type probing remains
available as a fallback but is not the design.

**Consequences.** The build-time stamping described above must be replaced: version identity moves from
`JVM.Constants.cs.tt` to an attribute emitted onto `IKVM.Java` by ikvmc, mirroring how real JDK 9 makes
`java.lang.VersionProps` the source of truth. One wrinkle constrains the implementation — `IKVM.Runtime-ref` never
receives the generated `JVM.Constants.cs`, because it excludes `..\IKVM.Runtime\obj\**\*.cs`. Consumers must stay
under `#if FIRST_PASS == false` or the bootstrap build breaks.

Two things genuinely cannot be done without a compile-time flag, and are handled otherwise: the residual typed
surface from ADR-1 (C# has no conditional type reference — handled by the `local/` overlay), and the class-file
*writer*, which is new code guarded by an option rather than a symbol.

### ADR-4 — JPMS modules are assembly metadata, not one assembly per module

**Context.** The obvious reading of JPMS is one .NET assembly per Java module. But `IKVM.Java` is already built three
times (per-OS) across three target frameworks, so a per-module split of `java.se` would mean roughly ninety projects.
A module is loaded by exactly one class loader, but a class loader may own arbitrarily many modules — so nothing
requires the split.

**Decision.** Modules are represented as assembly metadata. The per-.NET-module metadata channel already exists and
is exercised: `RuntimeAssemblyClassLoader.cs:106-111` reads `JavaModuleAttribute` per module, and `:1144` reads
`PackageListAttribute`, returning `(container, packages[])` pairs whose shape is already what a module table needs.

Two refinements:

*Naming.* Do **not** extend `JavaModuleAttribute`. In this codebase it means *.NET netmodule* —
`[AttributeUsage(AttributeTargets.Module)]`, stamped on dynamic modules by `DynamicClassLoader`, and used by
`RuntimeInit` to answer "is this a Java application". ikvmc's `targetIsModule` and `-target module` have the same
meaning. A JPMS attribute must carry a distinct name, e.g. `JpmsModuleAttribute`, so the distinction is unmissable.

*Encoding.* Descriptors are stored as **bytes, not attribute arguments**: ikvmc embeds the actual `module-info.class`
as a managed resource, plus a thin attribute listing the module names present. A `ModuleDescriptor` is
requires/exports/opens/uses/provides with modifiers and targets; encoding that positionally would be miserable, and
`PackageListAttribute(string jar, string[] packages)` is the cautionary precedent. Storing bytes means
`ModuleDescriptor.Read` — which already parses `Module`, `ModulePackages`, and `ModuleMainClass` from `IKVM.ByteCode`
— is reused verbatim at runtime. No new parsing, no encoding design, and a byte-exact round trip for ikvmstub.

**Consequences.** This pairs naturally with `IKVM.CoreLib.Modules` having readers but no writer — the writer is the
piece that must be built.

If a split ever does become necessary, it should follow module-graph boundaries. It should *not* follow the existing
`jdk`/`langtools`/`corba`/`jaxp`/`jaxws`/`nashorn` division: those are OpenJDK *repositories*, not modules, and the
`jdk` repo alone contains `java.base`, `java.desktop`, `java.logging`, `java.management`, `java.naming`, `java.rmi`,
`jdk.unsupported` and more.

### ADR-5 — The module graph is descriptive; class loading stays assembly-driven

**Context.** JPMS could plausibly *replace* IKVM's delegation model — module resolution deciding what is visible to
what — or merely *describe* it, answering reflective questions while `AssemblyClassLoader` continues to resolve
exactly as it does today. The two differ sharply in risk.

**Decision.** The module graph is descriptive. `AssemblyClassLoader` remains authoritative for class and resource
resolution. Modules exist to answer `Class.getModule()`, `Module.getName()`, `ServiceLoader` lookups, annotations
that read module state, and reflective access checks — not to decide whether a class can be found.

Three mechanics follow from the constraints verified above:

- **Modules are defined eagerly, at loader construction.** Because a package that has landed in a loader's unnamed
  module can never afterwards be claimed by a named module, definition must happen in
  `RuntimeAssemblyClassLoaderFactory.FromAssembly`, before any class in the assembly loads. The metadata is already
  in the assembly (ADR-4), so this needs no I/O beyond what the loader does anyway.
- **Each assembly forms its own layer**, parented to the boot layer. This falls out of one-loader-per-assembly and
  makes the per-loader package-uniqueness rule automatic. `-sharedclassloader` groups are the exception, and ikvmc
  already gives such a group a single package list.
- **Named modules implicitly read the unnamed modules of the assemblies their own assembly references**, applied via
  the same `jdk.internal.module.Modules.addReads` path the JDK uses for `--add-reads`. This mirrors the delegation
  graph IKVM already computes in `DoInitializeExports`.

**Alternatives rejected.**

*Making module resolution authoritative* — rejected because IKVM's delegation is deliberately forgiving and JPMS
resolution is not. `LoadAssemblyOrClearName` swallows every exception and caches the failure; a missing optional
dependency surfaces as `ClassNotFoundException` at the point of use. `Configuration.resolve` instead throws
`FindException` at layer creation. Adopting it would turn "an optional dependency is not deployed" into "the VM does
not start" for existing users, with no compensating benefit. The eager-definition constraint independently rules it
out anyway: the module graph cannot be the lazy mechanism even if that were desirable.

*Deriving a module per assembly automatically, for all assemblies* — rejected. It would make every `Assembly.Load` a
layer creation and force eager resolution of the assembly reference graph. Named modules are opt-in; assemblies
without module metadata contribute to their loader's unnamed module, exactly as today.

*Accepting that modular Java code cannot see .NET types* — rejected, though #665 leans toward accepting it on the
grounds that named modules cannot read the unnamed module. For IKVM specifically, reaching .NET code is the point of
the product, and the implicit-reads mechanism costs only the enforcement of strong encapsulation against non-modular
.NET assemblies — worth very little here.

**Consequences.** Strong encapsulation is weaker than a real JDK 9: code expecting `IllegalAccessError` when reaching
across an unexported boundary into .NET types will not get it. Resource encapsulation likewise stays assembly-shaped
rather than module-shaped. Both are deviations to state plainly in user documentation rather than paper over.

Because the boot layer's modules all live in the single `IKVM.Java` assembly, they are all defined to the bootstrap
loader, whereas a real JDK 9 splits them across the boot, platform, and application loaders via `ModuleLoaderMap`.
This is forced by shipping one assembly and is expected to be benign, but it is a real difference in
`Module.getClassLoader()` results.

## Non-goals

**Completing the `IKVM.CoreLib.Symbols` migration — deferred, not dismissed.** This is the larger multiplier on the
core compiler: 77 files carry `using Type = IKVM.Reflection.Type`, and collapsing the `IMPORTER`/`EXPORTER`
compilations would mean the type model is compiled and verified once rather than three times. That is a genuine
quality argument, not merely a convenience one — today a defect fixed on the runtime path can silently persist on the
importer path, because they are separate compilations of the same source.

It is nevertheless deferred, for a reason that survives principle 2: `ISymbol` and friends are interfaces, so the
abstraction imposes virtual dispatch on `RuntimeJavaType` and `ClassFile` — and those are used at *runtime* for
dynamic class loading, not only inside ikvmc. The trade is build-time correctness against runtime performance on a
path every dynamic-loading user exercises. That is a real trade-off rather than an effort question, and it deserves
its own investigation and its own measurements rather than being folded into the JDK 9 effort.

It is also genuinely independent of JDK 9: nothing in this document needs it. Sequencing it after the ADR-1 work
keeps each effort separately reviewable, which principle 1 favours.

**Side-by-side JDK 8 and JDK 9 in one process.** Precluded by ADR-2's identity constraint for as long as any
compile-time reference survives ADR-1.

**jtreg on the JDK 9 side, until the tree builds.** The jdk9 test tree is laid out differently, and
`JTRegTestManager` passes empty lists for all VM and compiler options, so `--add-modules` and `--add-exports` have
nowhere to go.

## Shape of the work

A map, not a schedule.

**Decoupling, first.** The contract verifier as a measurement instrument, then the four steps of ADR-1. All of it
ships as ordinary 8.x work with no JDK 9 tree in existence, and all of it is independently reviewable: step 1 is
deletion proven by compilation, step 2 is mechanical and proven by ikvmc still binding externs, step 3 uses a seam
that already exists.

**The rest of the 8.x-side preparation.** The externs namespace probe list — nothing in the JDK 9 tree can begin
without it. Parameterising the class-file ceiling. Moving version identity to a base-assembly attribute. Wiring
`IKVM.CoreLib.Modules` into ikvmc.

One caution on that last item: `ImportState.jars` is a *mutable* compilation structure — ikvmc calls `MarkAsStub()`
and `Remove()` on entries as compilation proceeds — whereas `ModuleFinder` and `ModuleReference` are read-only
discovery abstractions. The module machinery should be **layered alongside** the existing `Jar` structure, resolving
a module path and producing `Jar`s, not presented as a replacement for it. Framing it as a replacement is how that
change becomes too large to review.

**The JDK 9 tree.** A second submodule, per-flavor `OpenJdk*` properties (keeping `OpenJdkDir` as the JDK 8 default
so the 54 files referencing it are untouched), a JDK 9 build-tools target file, and an `IKVM.Java9` project family
following the existing `<Name>.runtime.<os>` convention.

Scope the first milestone to `java.base` alone — not to reach something sooner, but because `java.base` is the one
subset that is meaningful in isolation: it is a complete, specified module, so "does `java.base` transpile and
initialise" is a question with a real answer. Most of the overlay carries over: of `map.xml`'s 69 remapped classes,
all but two are `java.base` in JDK 9 — the exceptions being `javax.swing.SwingUtilities` and
`com.sun.xml.internal.ws.developer.ServerSideException`. Of the 119 `local/` files, 13 are the `sun/jdbc/odbc` bridge
and 2 are management classes; 29 are IKVM's own `ikvm/*` types that carry over regardless.

Set the milestone as *"the contract verifier reports zero unresolved references and `JVM.Init()` completes"*, not
"Hello World". This is about what a checkpoint is *for*: printing a string reaches charset handling, `sun.nio.cs`,
`PrintStream`, and the generated NIO buffer classes — most of the 1,907-line generator file — so "Hello World" does
not isolate a failure, it aggregates the whole port into one pass/fail. `JVM.Init()` completing tells you the
runtime and the base library agree; that is a diagnosis, not a score.

The JDK 9 build-tools target file deserves its own effort rather than being treated as a copy with edits: JDK 9's
build tools are themselves modular and compile against `jdk.compiler` internals that JDK 9 does not export, so they
need a hand-curated `--add-exports` list, and some were rewritten outright.

**Native libraries.** Scope to the handful `java.base` needs — `libjvm`, `libiava`, `libzip`, `libnet`, `libnio`,
`libverify`, `libfdlibm`, `libmanagement`. Because JDK 9 restructured the native tree completely, these are new
project files rather than parameterised existing ones. Each needs its own `IKVM.Java9.runtime.<os>` project reference
to obtain `javac -h` JNI headers, and output-path collisions are a hazard because the JDK 9 header producer has the
same assembly name.

**Runtime JPMS.** Boot layer construction, `initPhase1`/`initPhase2`/`initPhase3` selected by feature version, a
`RuntimeModule` type mirroring `IKVM.CoreLib.Modules`, the eager per-assembly module definition of ADR-5, and the
module-descriptor *writer* that ikvmc and ikvmstub both need.

**Continuous integration.** The JDK 9 build must be a separate, opt-in job with its own entry project — not an
addition to `IKVM.dist.msbuildproj`, and not a second target inside `build-ikvm`. This is a hard resource limit
rather than a preference: `build-ikvm` already runs against a 720-minute ceiling with manufactured swap and
aggressive disk cleanup, so folding a second tree into it would destabilise the 8.x build — which principle 1
forbids. Restricting the new job via the existing `EnabledRuntimes` knob to a single RID keeps it within capacity.

## JEP triage

Issue #120 tracks a checklist of JDK 9 JEPs. The question this table answers is not which are cheapest but which can
be delivered *completely and conformantly* at a given stage — a JEP that can only be half-implemented before the JDK 9
tree exists should wait for it, per principle 1.

| JEP | Needs the JDK 9 tree? | Assessment |
| --- | --- | --- |
| [238](https://openjdk.org/jeps/238) Multi-Release JARs | No | Can be delivered completely on the 8 line: it is a tooling capability, not a library API, so it introduces no non-conformance. The plumbing in `JarFile.cs` is written and merely short-circuited. It also has the largest practical effect on existing users, who encounter multi-release jars in modern third-party libraries. |
| [213](https://openjdk.org/jeps/213) Milling Project Coin | No | Follows from raising the class-file ceiling. Note precisely what this means: IKVM would *consume* v53 class files, not *emit* them, because `src/javac` is transpiled OpenJDK 8 javac. That asymmetry should be stated in release notes, or users will reasonably read "JEP 213" as "I can write this syntax". |
| [285](https://openjdk.org/jeps/285) Spin-Wait Hints | No | One `local/` method and one extern to `Thread.SpinWait`, fully conformant. Adds `Thread.onSpinWait` to the 8 line, which is a documented divergence from Java 8 — small, but it belongs in the same release-notes discipline as JEP 213. |
| [261](https://openjdk.org/jeps/261) Module System | Partly | The ikvmc-side module graph needs no tree; the runtime side does. See ADR-4 and ADR-5. |
| [274](https://openjdk.org/jeps/274) Enhanced MethodHandles | Yes | Pure Java additions to `java.base`; arrives with the tree and cannot be delivered conformantly without it. |
| [259](https://openjdk.org/jeps/259) Stack-Walking | Yes | The supporting internals already exist, but lazy frame traversal is a fundamentally different implementation from IKVM's eager `StackTraceElement[]` model. Implementing `StackWalker` eagerly would satisfy the API and violate its purpose. |
| [193](https://openjdk.org/jeps/193) Variable Handles | Yes | `VarHandle` is intertwined with `MethodHandle`, `LambdaForm` and `MemberName` — the same cluster ADR-1 holds as the residual core, and all of them are in `map.xml`'s remap list. The most structurally entangled item on the list, and the one most likely to reopen ADR-1. |
| [102](https://openjdk.org/jeps/102) Process API | Yes | Implementable against `System.Diagnostics.Process`, but shipping `ProcessHandle` on a Java 8 runtime advertises an API the platform does not have. |
| [267](https://openjdk.org/jeps/267) Unicode 8.0 | No | **Should not be done on the 8 line.** Java 8 specifies Unicode 6.2; regenerating the character data to 8.0 would make `Character`, `String.toUpperCase`, and the break iterators diverge from the specification IKVM 8.x claims to implement. This is a conformance argument, not a value one — it belongs with the JDK 9 tree, where Unicode 8.0 *is* the specification. |

[246](https://openjdk.org/jeps/246) (GHASH/RSA CPU instructions) is already complete.

The three items deliverable on the 8 line share a property worth naming: each of them makes IKVM 8.x diverge from
Java 8, in the direction of Java 9. That is defensible — IKVM has always shipped some things Java 8 does not have —
but it is a divergence, and principle 4 says it belongs in user documentation rather than in a changelog entry.

## Open questions

Things this document asserts on inspection but has not proven:

- How far ADR-1 actually gets. The step-by-step reduction is grounded in file counts, but no step has been attempted;
  the residual core could prove larger than the 12 `java.lang.invoke` types once `ByteCodeHelper` is worked through.
- Whether IKVM's JSR292 support surface can be relocated into `IKVM.Runtime`, as ADR-1 speculates. The types IKVM
  patches must *be* `java.lang.invoke` types as far as Java code is concerned, so the question is how much of the
  supporting machinery can move without them ceasing to be. If a meaningful amount can, ADR-1's residual core
  shrinks further and the identity constraint in ADR-2 weakens with it.
- Whether the `IKVM.CoreLib.Symbols` trade-off is real as stated. The claim that interface dispatch on
  `RuntimeJavaType`/`ClassFile` would measurably regress dynamic class loading is asserted from the shape of the
  abstraction, not measured. If it turns out to be negligible — or removable by generic specialisation — the
  deferral in [Non-goals](#non-goals) should be revisited, because the build-time correctness argument for it is
  strong.
- Whether loosening extern signatures to `object` has a measurable cost. `IsCompatibleArgList` permits it, but the
  emitted call sites gain casts, and some externs are hot.
- Whether `IKVM.ByteCode` silently skips class-file attributes it does not recognise. If not, reading a v53 class
  carrying `Module` or `NestHost` will throw even after the ceiling is raised, making attribute handling a
  prerequisite rather than a later refinement.
- Whether `src/IKVM.Tools.Importer/Jar.cs` shares any code path with `src/IKVM.CoreLib/Jar/JarFile.cs`. It appears
  not to — ikvmc reads zip entries directly — which would make multi-release support a larger change than flipping
  the four constants suggests.
- Whether `RUNTIME_VERSION` being `static readonly` causes problems once it must mean "the version being targeted"
  rather than "the version we are", particularly for ikvmc, where a single process may need more than one value.
- What a layer per assembly costs at scale. ADR-5 creates a `ModuleLayer` per modular assembly; layer creation is not
  free. Non-modular assemblies are unaffected, so exposure is bounded by how much modular Java a program loads — but
  the constant is unmeasured.
- How eager resolution interacts with lazy assembly loading in practice. A modular assembly's `requires` must resolve
  when its layer is created, forcing referenced modular assemblies to load earlier than they would today.
- Whether resource encapsulation can stay assembly-shaped without breaking `ServiceLoader` and
  `Class.getResourceAsStream` in ways real JDK 9 code depends on.
