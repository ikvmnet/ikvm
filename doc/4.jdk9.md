# JDK 9

IKVM currently implements Java SE 8. This document describes how JDK 9 support can be added *alongside* the existing
JDK 8 support — built from the same repository and the same branch — and records the architectural decisions that
make that possible.

It is a design document, not a work plan. It exists because the JDK 9 effort is large enough to span many releases,
and work spread over that long a period needs a written account of why things are shaped the way they are. Tracking
issues [#120](https://github.com/ikvmnet/ikvm/issues/120) and [#665](https://github.com/ikvmnet/ikvm/issues/665)
carry the discussion; this carries the conclusions.

## The problem

Adding JDK 9 is not one change. It touches:

- the `ext/openjdk` submodule, which is pinned to `ikvmnet/jdk8u`;
- `src/IKVM.Java/IKVM.Java.runtime.jdk.{props,targets}`, ~2,300 lines of MSBuild that hand-port the OpenJDK 8
  makefiles, including 31 code-generation targets;
- `src/IKVM.Java/map.xml`, 2,899 lines remapping 69 Java classes onto CLR types;
- `src/IKVM.Java/local/`, 119 hand-written `.java` files replacing OpenJDK classes;
- 36 `.clangproj` native library projects, whose source globs assume the JDK 8 layout;
- `IKVM.Runtime`, 425 files and ~95,000 lines, compile-time bound to roughly 180 JDK-8-shaped types.

None of that can land at once. The organising question for this document is therefore not "how do we implement JDK 9"
but **"how do we arrange the repository so that JDK 9 work can arrive in small pieces, over years, without
destabilising the shipping 8.x line."**

Two properties follow from that framing and shape everything below:

1. As much work as possible should happen *inside the JDK 8 tree*, shipping as ordinary 8.x improvements, before any
   second source tree exists.
2. The second tree, when it arrives, must be opt-in and unpublished until it actually runs — visible to CI, invisible
   to users.

## What the code looks like today

The decisions in this document are constrained by things already true of the codebase. The load-bearing ones:

### A JPMS implementation already exists, and nothing uses it

`src/IKVM.CoreLib/Modules/` is 31 files and 4,861 lines — a C# port of `java.lang.module` and `jdk.internal.module`.
It contains `ModuleDescriptor` and its builder, `ModuleFinder`/`ModulePath` (handling modular jars, exploded modules,
and automatic modules including `Automatic-Module-Name`), `JarModuleReader`, `ExplodedModuleReader`,
`InMemoryModuleFinder`, a 663-line `ModuleResolver`, `ModuleConfiguration`, and a full JEP 223 `RuntimeVersion`
parser. Its `README.txt` states the intent plainly:

> The importer and exporter will use this to build a module graph from existing Java code for transpilation.

It is tested end to end: `src/IKVM.CoreLib.Tests/Modules/` builds fixtures with JDK 21
`javac --release 9 -p …` into `src/IKVM.CoreLib.Tests/res/Modules/{m1,m2,m3,m4,automatic}`.

It is referenced only by `IKVM.Util/Jar/*`, `IKVM.CoreLib/Jar/JarFile.cs`, and
`IKVM.MSBuild.Tasks/IkvmReferenceItemPrepare.cs`. Neither `IKVM.Tools.Importer`, nor `IKVM.Tools.Exporter`, nor
`IKVM.Runtime` touches it. It has readers but no writer.

In other words, the compiler-side half of [#665](https://github.com/ikvmnet/ikvm/issues/665) is largely written and
merely unwired — and wiring it requires no JDK 9 source tree at all.

### Externs bind through a single hard-coded namespace

Native methods are implemented in C# under `src/IKVM.Runtime/Java/Externs/` and bound by ikvmc at static-compile
time. The binding is one line, `src/IKVM.Runtime/RuntimeByteCodeJavaType.FinishContext.cs:395`:

```csharp
var nativeCodeType = context.Resolver.ResolveRuntimeType("IKVM.Java.Externs." + classFile.Name.Replace("$", "+")).AsReflection();
```

A single root, resolved by exact name. This matters because it is tempting to assume a second extern tree could
simply be added alongside the first — it cannot. The two trees would collide on precisely the classes that need
different bodies (`java.lang.System`, `Class`, `Thread`, `ClassLoader`, `sun.misc.Unsafe`, `java.lang.invoke.*`).
The extern tree is also internally cross-coupled by direct C# calls between extern classes, so it is not a clean
unit to copy either.

Making that root an ordered probe list is the smallest change that unblocks a second tree, and it does not exist yet.

### The runtime's reference assembly carries no metadata

`IKVM.Runtime.csproj` has a `ProjectReference` to `IKVM.Java.ikvmproj`, whose `ConvertRefAssembly` target runs
refasmer with `--refasm --overwrite --noattr --all`. The assembly `IKVM.Runtime` compiles against therefore contains
type and member *shapes* only. Every part of the metadata contract — `RemappedClassAttribute`, `PackageListAttribute`,
class maps — is discovered at runtime from whichever assembly is actually loaded, via `AttributeHelper`.

This is what makes a single runtime binary feasible. It is also the source of the main risk: `IKVM.Runtime` is
*compiled against* one base library and merely *loaded against* another, so the ~180 direct `global::java.*` and
`global::sun.*` references become runtime `TypeLoadException`/`MissingMethodException` risks with no build-time
proof. Drift on a package-private member surfaces as a failure deep inside `JVM.Init()`.

### Version ceilings are narrower than they look

`src/IKVM.Runtime/ClassFile.SupportedVersions.cs` declares `Minimum = 45` and `Maximum = 52`, but the type has no
references anywhere in the tree outside its own declaration — it is dead code. The only live ceilings are two
literals:

```
src/IKVM.Runtime/ClassFile.cs:357   if (reader.Version < new ClassFormatVersion(45, 3) || reader.Version > 52)
src/IKVM.Runtime/ClassFile.cs:386   if (clazz.Version  < new ClassFormatVersion(45, 3) || clazz.Version  > 52)
```

Every other version test in the codebase — `< 49`, `< 51`, `>= 52` across `ClassFile.*`, `MethodAnalyzer.cs`,
`compiler.cs`, `RuntimeByteCodeJavaType.JavaTypeImpl.cs` — is a *backward*-compatibility gate. Those stay correct
verbatim as the ceiling rises; they do not need auditing.

Note that `ClassFile.cs:357` is the IMPORTER-only `GetClassName`, which ikvmc calls on every input file. A v53
`module-info.class` therefore fails before ikvmc ever inspects it. Module class files must bypass
`IKVM.Runtime.ClassFile` entirely and go to `ModuleDescriptor.Read`, which consumes the raw `IKVM.ByteCode` class
file.

### The Java version is stamped into the runtime at build time

`src/IKVM.Runtime/JVM.Constants.cs.tt` is token-substituted during the build from the global `OpenJdk*` properties in
`Directory.Build.props`, producing `java_version`, `java_specification_version`, `java_runtime_version` and friends.
`JVM.Properties.InitSystemProperties` consumes them, and also sets `java.ext.dirs`, `java.endorsed.dirs`, and
`sun.boot.class.path` — all JDK 8 concepts with no meaning under JPMS.

A runtime binary shared between flavors cannot be stamped `1.8`.

### The bootstrap chain multiplies every runtime change

IKVM breaks the `IKVM.Java` ↔ `IKVM.Runtime` cycle with a four-stage bootstrap: `IKVM.Java-ref` (61 hand-written C#
stubs) → `IKVM.Runtime-ref` (all of `../IKVM.Runtime/**/*.cs` recompiled with `FIRST_PASS`) → `IKVM.Java` (ikvmc,
`-bootstrap`) → `IKVM.Runtime`. `IKVM.Tools.Importer` and `IKVM.Tools.Exporter` are two further compilations of the
same sources under `IMPORTER` and `EXPORTER`.

Six compilations, across three target frameworks. Any change to `IKVM.Runtime` must survive all of them, and a
change that satisfies one can break another in ways the diff does not show.

### Other constraints worth stating

- `src/IKVM.NET.Sdk/targets/IKVM.Java.props` sets `<LangVersion>1.8</LangVersion>` and `<JavaVersion>1.8</JavaVersion>`
  unconditionally, so no project — in this repo or in a consumer's — can override them.
- `targets/openjdk.buildtools.targets` compiles the OpenJDK build tools with `-source 1.8 -target 1.8` and requires
  `$(JdkPath)/lib/tools.jar`. JDK 9 has no `tools.jar`, moved the build tools to `make/jdk/src/classes`, and does not
  export the `jdk.compiler` internals they use.
- `targets/openjdk.lib.props` maps RIDs to `windows`/`solaris` source directories. JDK 9 restructured the native
  layout entirely (`src/java.base/{share,unix,windows,macosx}/native/libjava/…`), invalidating all 36 clangproj globs.
- `FindJdk Family="8"` appears in `src/IKVM.Java/IKVM.Java.runtime.targets`,
  `src/IKVM.Image/IKVM.Image.project.targets`, and `src/javac-ref/javac-ref.ikvmproj`. `IKVM.CoreLib.Tests` already
  uses `Family="21"`, and CI already installs `openjdk-21-jdk` without using it.
- `ikvmc` does not use `IKVM.CoreLib.Jar.JarFile`. `ImportContext.ProcessZipFile` calls `ZipFile.OpenRead` directly,
  and `ProcessManifest` reads only `Main-Class:`.
- `IKVM.CoreLib/Jar/JarFile.cs:23-27` pins `BASE_VERSION` and `RUNTIME_VERSION` to `8` and sets
  `MULTI_RELEASE_ENABLED = false`. The versioned-entry plumbing behind those pins is written and simply
  short-circuited.
- CI builds everything in one `build-ikvm` job with a 720-minute timeout, cross-compiling 11 RIDs, already requiring
  manufactured swap space and aggressive disk cleanup. It cannot absorb a second full build.

## Decisions

### ADR-1 — One `IKVM.Runtime.dll` serves both JDK flavors

**Context.** `IKVM.Runtime` is the largest and most intricate component. Forking it per JDK version would double the
maintenance surface of the hardest code in the project, and the bootstrap chain means the fork would really be twelve
compilations rather than six.

**Decision.** Ship one `IKVM.Runtime.dll`. It continues to compile against the JDK 8 `IKVM.Java` reference assembly.
The JDK 9 `IKVM.Java` must be a **superset of the referenced surface**.

**Alternatives rejected.** Forking the runtime per flavor — rejected on maintenance cost. Making the runtime
JDK-agnostic by removing all direct typed references — rejected because the `java.lang.invoke` references sit on the
MethodHandle hot path and several are IL-*emission* sites, where indirection changes generated code rather than
merely slowing it.

**Consequences.** The superset property is a permanent invariant that every future JDK bump inherits, and it is
enforced by nothing today. It must be checked mechanically — walking `IKVM.Runtime.dll`'s TypeRef/MemberRef tables for
references into assembly `IKVM.Java` and resolving each against a candidate base library. IKVM.Reflection is already
a dependency, so this is a small tool, and it doubles as the worklist generator for the porting work: it says exactly
which types and members the JDK 9 tree must supply.

### ADR-2 — The JDK 9 `IKVM.Java` keeps `AssemblyVersion = 8.0.0.0`

**Context.** All assemblies are strong-named from the checked-in `ikvm.snk`. `AssemblyVersion` derives from
`DefaultMajorVersion`, which is `8` — and by convention IKVM's major version tracks the Java version it implements.
The natural-looking move is therefore to build the JDK 9 flavor as `9.0.0.0`.

**Decision.** It stays `8.0.0.0`. The "9-ness" lives in the `OpenJdk*` MSBuild properties and in a base-assembly
attribute, never in `AssemblyVersion`. `DefaultMajorVersion` is not touched.

**Alternatives rejected.** Bumping to `9.0.0.0` — rejected because `IKVM.Runtime.dll` carries a baked `AssemblyRef`
to `IKVM.Java, Version=8.0.0.0`. .NET Core has no publisher policy, so the reference would simply fail to resolve,
and .NET Framework would need binding redirects. This directly contradicts ADR-1.

**Consequences.** The two flavors share an assembly identity and are therefore **mutually exclusive** — on disk, in a
NuGet package, and in a process. They need separate output roots and separate test processes. There is no
side-by-side story, and none is planned; an application picks a Java version.

### ADR-3 — No new conditional-compilation symbol

**Context.** `IKVM.Runtime` is already compiled six times under different symbols (`FIRST_PASS`, `IMPORTER`,
`EXPORTER`, and the plain build), across three target frameworks. `FIRST_PASS` alone appears 680 times across 191 of
425 files.

**Decision.** JDK-flavor differences are expressed as **data**, not as C# conditionals: MSBuild source globs,
`map.xml`, and the `local/` overlay. Where the runtime genuinely must behave differently, it branches on a single
integer feature version read once from an attribute on the loaded base assembly.

**Alternatives rejected.** A seventh compilation symbol — rejected; it compounds the bootstrap problem and every
future change would need testing under both. Runtime capability probing ("does `java.lang.Module` exist?") — rejected
as both fragile and *late*: by the time `JVM.Init()` runs, boot decisions have already been made. Type probing
remains available as a fallback but is not the design.

**Consequences.** The build-time stamping described above must be replaced: the version identity moves from
`JVM.Constants.cs.tt` to an attribute emitted onto `IKVM.Java` by ikvmc, mirroring how real JDK 9 makes
`java.lang.VersionProps` the source of truth. One wrinkle constrains the implementation — `IKVM.Runtime-ref` never
receives the generated `JVM.Constants.cs`, because it excludes `..\IKVM.Runtime\obj\**\*.cs`. Consumers must
therefore stay under `#if FIRST_PASS == false` or the bootstrap build breaks.

Three things genuinely cannot be done without a compile-time flag, and are handled by other means instead: the direct
typed surface itself (C# has no conditional type reference — handled by the `local/` overlay per ADR-5); the
`java.lang.invoke` IL-emission sites (same); and the class-file *writer*, which is new code guarded by an option
rather than a symbol.

### ADR-4 — JPMS modules are assembly metadata, not one assembly per module

**Context.** The obvious reading of JPMS is one .NET assembly per Java module. But `IKVM.Java` is already built three
times (per-OS) across three target frameworks, so a per-module split of `java.se` would mean roughly ninety projects.
wasabii's own note on #665 observes that an assembly can perfectly well hold several modules under a single
`AssemblyClassLoader`, since a module is loaded by one class loader but a class loader may own many modules.

**Decision.** Modules are represented as assembly metadata. The per-.NET-module metadata channel already exists and
is exercised — `RuntimeAssemblyClassLoader.cs:106-111` reads `JavaModuleAttribute` per module, and `:1144` reads
`PackageListAttribute`, returning `(container, packages[])` pairs whose shape is already what a module table needs.

Two refinements:

*Naming.* Do **not** extend `JavaModuleAttribute`. In this codebase it means *.NET netmodule* —
`[AttributeUsage(AttributeTargets.Module)]`, stamped on dynamic modules by `DynamicClassLoader`, and used by
`RuntimeInit` to answer "is this a Java application". ikvmc's `targetIsModule` and `-target module` have the same
meaning. A JPMS attribute must carry a distinct name, e.g. `JpmsModuleAttribute`, so the distinction is unmissable.

*Encoding.* Descriptors are stored as **bytes, not attribute arguments**: ikvmc embeds the actual
`module-info.class` as a managed resource, plus a thin attribute listing the module names present. A
`ModuleDescriptor` is requires/exports/opens/uses/provides with modifiers and targets; encoding that positionally
would be miserable, and `PackageListAttribute(string jar, string[] packages)` is the cautionary precedent. Storing
bytes means `ModuleDescriptor.Read` — which already parses `Module`, `ModulePackages`, and `ModuleMainClass` from
`IKVM.ByteCode` — is reused verbatim at runtime. No new parsing, no encoding design, and a byte-exact round trip for
ikvmstub.

**Consequences.** This is what makes the module work cheap, and it pairs naturally with `IKVM.CoreLib.Modules` having
readers but no writer — the writer is the piece that must be built.

If a split ever does become necessary, it should follow module-graph boundaries. It should *not* follow the existing
`jdk`/`langtools`/`corba`/`jaxp`/`jaxws`/`nashorn` division: those are OpenJDK *repositories*, not modules, and the
`jdk` repo alone contains `java.base`, `java.desktop`, `java.logging`, `java.management`, `java.naming`, `java.rmi`,
`jdk.unsupported` and more.

### ADR-5 — The JDK 9 tree may carry an IKVM-private compatibility surface

**Context.** ADR-1 requires the JDK 9 base library to be a superset of what `IKVM.Runtime` references. Some of those
references are to types JDK 9 removed or moved — most visibly `sun.reflect.*`, which became `jdk.internal.reflect.*`.

**Decision.** The JDK 9 tree's `local/` overlay may add back IKVM-private types to satisfy the referenced surface,
carrying both the real `jdk.internal.reflect.Reflection` and an IKVM-private `sun.reflect.Reflection`.

**Alternatives rejected.** A plain forwarder class is not sufficient for everything: `sun.reflect.Reflection` and
`sun.invoke.util.VerifyAccess` are among `map.xml`'s 69 remapped classes, meaning their bodies are injected by ikvmc
rather than compiled. A remap cannot be replaced by a forwarder.

**Consequences.** This is a **deliberate and permanent** part of the design, not a temporary shim to be cleaned up
later. It should be documented as such wherever those types are defined, so a future contributor does not "fix" it by
deleting them. IKVM already forks OpenJDK heavily — 119 `local/` files and a 2,899-line `map.xml` — so this is
consistent with how the project already works rather than a new kind of debt.

## Shape of the work

The decisions above imply a rough ordering. This is a map, not a schedule.

**Inside the JDK 8 tree.** Everything here ships as ordinary 8.x work and requires no second source tree. The
externs namespace probe list comes first, because nothing in the JDK 9 tree can begin without it. Parameterising the
class-file ceiling and moving version identity to a base-assembly attribute are independent and small. The contract
verifier from ADR-1 belongs here too, and should be built early: run JDK 8 against JDK 8 first, where it must report
zero unresolved references, which proves the tool before anyone trusts it against JDK 9. Wiring
`IKVM.CoreLib.Modules` into ikvmc — #665 Step 1 — also belongs here.

One caution on that last item. `ImportState.jars` is a *mutable* compilation structure: ikvmc calls `MarkAsStub()`
and `Remove()` on entries as compilation proceeds. `ModuleFinder` and `ModuleReference` are read-only discovery
abstractions. The module machinery should be **layered alongside** the existing `Jar` structure — resolving a module
path and producing `Jar`s — not presented as a replacement for it. Framing it as a replacement is how that change
becomes too large to review.

A related caution: it is tempting to prepare for JDK 9 by systematically moving the direct typed references behind
the existing accessor layer. On an 8-only codebase that produces no observable change and no test signal, while
risking the MethodHandle path — it is unverifiable work. The contract verifier inverts this: it produces the actual
list of members JDK 9 must supply, so each one can be shimmed or accessor-ised against a failing build.

**The JDK 9 tree.** A second submodule, per-flavor `OpenJdk*` properties (keeping `OpenJdkDir` as the JDK 8 default
so the 54 files referencing it are untouched), a JDK 9 build-tools target file, and an `IKVM.Java9` project family
following the existing `<Name>.runtime.<os>` convention.

Scope the first milestone to `java.base` alone. The overlay cost is smaller than the raw counts suggest: of
`map.xml`'s 69 remapped classes, all but two are `java.base` in JDK 9 — the exceptions being
`javax.swing.SwingUtilities` and `com.sun.xml.internal.ws.developer.ServerSideException`. Of the 119 `local/` files,
13 are the `sun/jdbc/odbc` bridge and 2 are management classes; 29 are IKVM's own `ikvm/*` types that carry over
regardless.

Set the milestone as *"the contract verifier passes and `JVM.Init()` completes"*, not "Hello World". Printing a
string reaches charset handling, `sun.nio.cs`, `PrintStream`, and the generated NIO buffer classes — that is most of
the 1,907-line generator file, and it makes the first milestone far larger than it needs to be.

The JDK 9 build-tools target file deserves its own effort rather than being treated as a copy with edits: JDK 9's
build tools are themselves modular and compile against `jdk.compiler` internals that JDK 9 does not export, so they
need a hand-curated `--add-exports` list, and some were rewritten outright.

**Native libraries.** Scope to the handful `java.base` needs — `libjvm`, `libiava`, `libzip`, `libnet`, `libnio`,
`libverify`, `libfdlibm`, `libmanagement`. Because JDK 9 restructured the native tree completely, these are new
project files rather than parameterised existing ones; the two layouts have nothing in common. Each needs its own
`IKVM.Java9.runtime.<os>` project reference to obtain `javac -h` JNI headers, and output-path collisions are a real
hazard because the JDK 9 header producer has the same assembly name.

**Runtime JPMS.** The boot layer, `initPhase1`/`initPhase2`/`initPhase3` selected by feature version, a
`RuntimeModule` type mirroring `IKVM.CoreLib.Modules`, and the module-descriptor *writer* that ikvmc and ikvmstub
both need.

**Continuous integration.** The JDK 9 build must be a separate, opt-in job with its own entry project — not an
addition to `IKVM.dist.msbuildproj`, and not a second target inside `build-ikvm`. Restricting it via the existing
`EnabledRuntimes` knob to a single RID keeps it affordable. jtreg on the JDK 9 side is explicitly out of scope until
the tree builds: the jdk9 test tree is laid out differently, and `JTRegTestManager` currently passes empty lists for
all VM and compiler options, so `--add-modules` and `--add-exports` have nowhere to go.

## JEP triage

Issue #120 tracks a checklist of JDK 9 JEPs. They differ enormously in whether they need the second source tree.

| JEP | Needs the JDK 9 tree? | Assessment |
| --- | --- | --- |
| [238](https://openjdk.org/jeps/238) Multi-Release JARs | No | Best value for effort on the list. Pure tooling, and the plumbing in `JarFile.cs` is written and merely short-circuited. Unblocks consuming modern third-party jars on the 8 line, which is what users actually encounter. |
| [213](https://openjdk.org/jeps/213) Milling Project Coin | No | Falls out of the class-file ceiling work almost free. Note precisely what this means: IKVM would *consume* v53 class files, not *emit* them — `src/javac` is transpiled OpenJDK 8 javac. |
| [285](https://openjdk.org/jeps/285) Spin-Wait Hints | No | One `local/` method and one extern to `Thread.SpinWait`. Near-free and near-zero value; a good first contribution. |
| [261](https://openjdk.org/jeps/261) Module System | Partly | The ikvmc-side module graph needs no tree; the runtime side does. |
| [274](https://openjdk.org/jeps/274) Enhanced MethodHandles | Yes | Pure Java additions to `java.base` — essentially free once the tree builds, and impractical without it. |
| [259](https://openjdk.org/jeps/259) Stack-Walking | Yes | The supporting internals already exist, but lazy frame traversal is a fundamentally different implementation from IKVM's eager `StackTraceElement[]` model. |
| [193](https://openjdk.org/jeps/193) Variable Handles | Yes | `VarHandle` is intertwined with `MethodHandle`, `LambdaForm`, and `MemberName` — all of which are in `map.xml`'s remap list. Cannot be bolted onto the 8 fork without rewriting the remap. Highest effort on the list. |
| [102](https://openjdk.org/jeps/102) Process API | Yes | Implementable against `System.Diagnostics.Process`, but shipping `ProcessHandle` on a Java 8 runtime advertises an API the platform does not have. |
| [267](https://openjdk.org/jeps/267) Unicode 8.0 | No | Recommend skipping. Pure data regeneration, low value, and it changes `Character` behaviour for the shipping 8 product — the worst risk-to-reward ratio here. |

[246](https://openjdk.org/jeps/246) (GHASH/RSA CPU instructions) is already complete.

## Open questions

Things this document asserts on inspection but has not proven:

- Whether `IKVM.ByteCode` silently skips class-file attributes it does not recognise. If it does not, reading a v53
  class carrying `Module` or `NestHost` will throw even after the ceiling is raised, and attribute handling becomes a
  prerequisite rather than a later refinement.
- Whether `src/IKVM.Tools.Importer/Jar.cs` shares any code path with `src/IKVM.CoreLib/Jar/JarFile.cs`. It appears
  not to — ikvmc reads zip entries directly — which would make multi-release support a larger change than flipping
  the four constants suggests.
- Whether `RUNTIME_VERSION` being `static readonly` causes problems once it must mean "the version being targeted"
  rather than "the version we are", particularly for ikvmc, where a single process may need more than one value.
- How JDK 9's module system interacts with IKVM's existing `ikvm.runtime.AssemblyClassLoader` delegation model
  (see [Class Loading](3.classloading.md)), where statically compiled code has no class loader hierarchy and
  resolution follows .NET assembly references instead. The module graph and that delegation model are two different
  answers to the same question, and the interaction is not yet designed.
